# BountyVault 开发约定

> 本文档约定团队日常开发的工作方式，随项目演进可经 issue 讨论后修订。
> 制定依据：项目负责人在 DAPP-1 评论中的补充要求（2026-09-15）。

## 1. 语言约定

| 产物类型 | 语言 |
|---|---|
| 平时开发文档（设计稿、API 草案、会议纪要、测试计划、本文件等内部文档） | 中文 |
| 课程交付物（README、项目报告 PDF、演示 slides、演示视频） | 英文 |
| 代码及代码注释（属于课程评阅的源码一部分） | 英文 |
| Multica issue 讨论、PR 讨论 | 中文 |

说明：`docs/PRD.md` 与 `docs/ARCHITECTURE.md` 是按 DAPP-1 明确要求用英文撰写的，
保持不变；之后新增的开发文档一律使用中文。

## 2. 工程纪律（留痕与谨慎修改）

1. **一切变更先有 issue**：任何代码或文档修改都对应一个 Multica issue，说明动机与验收标准；
   无 issue 不改代码。
2. **一切变更走 PR**：不直接推送 `main`。PR 标题带 issue key（如 `[DAPP-1] ...`），
   不使用 `Fixes/Closes` 等 closing keyword（issue 的关闭由人验收后手动进行）。
3. **小步提交**：每个 commit 只做一件事，commit message 遵循约定式提交
   （如 `feat: ...` / `fix: ...` / `docs: ...`），正文说明原因，末尾 `Refs: <issue key>` 留痕。
4. **谨慎修改**：改动范围最小化，不顺手重构无关代码；修改前先读懂周边代码与既有约定；
   修改后运行相关测试或构建验证，验证结果写入 PR 描述。
5. **历史不可篡改**：不 force-push、不改写已推送历史；需要修正就追加新的 commit。
6. **重要决策留痕**：技术选型、接口变更、范围调整等决策记录在对应 issue 的评论中，
   必要时沉淀到 `docs/`。
7. **审查后合并**：PR 至少经一名非作者成员审查通过后合并；合并用 squash 或 merge commit
   均可，但保持主干历史可读。
